# Pairper 수정 지시서 — Secure MCP Tunnel 자동 연결 및 TypeScript UI 전환

## 1. 작업 목적

Pairper는 AI와 함께 논문을 읽고 이해하기 위한 로컬 데스크톱 프로그램이다.

현재 GitHub 저장소:
https://github.com/srejis/Pairper.git

현재 코드는 Python, PySide6, QtWebEngine, PyMuPDF, SQLite 및 MCP Python SDK로 구현되어 있다.

이번 작업은 기존 기능을 다시 만드는 것이 아니다.

다음 두 가지를 개선한다.

1. **Secure MCP Tunnel을 Windows 로그인 시 자동 연결하고, 인증 정보를 프로젝트별 로컬 파일로 관리한다.**
2. **기존 Python 백엔드를 최대한 유지하면서 사용자 인터페이스와 논문 렌더러를 TypeScript 기반으로 전환한다.**

우선순위는 MCP 연결이다. MCP 연결이 정상 작동하는 것을 먼저 검증하고 UI 전환을 진행한다.

한국어 번역, 논문 해설, 새로운 AI 분석 기능은 이번 범위에 포함하지 않는다.

# Part A. Secure MCP Tunnel 자동 연결

## 3. 기존 연결 방식의 문제

현재 문서는 PowerShell에서 API 키를 환경변수에 수동 입력하고, 터널 클라이언트를 직접 실행하도록 안내한다.

이 방식은 초기 연결 테스트에는 사용할 수 있지만 실제 Pairper 사용 방식에는 맞지 않는다.

사용자는 다음 동작을 원한다.

- Windows 로그인 시 별도 조작 없이 MCP 자동 연결
- 로그인할 때마다 API 키를 다시 입력하지 않음
- 다른 프로젝트의 API 키와 섞이지 않음
- 사용자 또는 시스템 전체 영구 환경변수에 키를 등록하지 않음
- 로컬 Pairper 프로그램 창이 닫혀 있어도 MCP 사용 가능
- 연결 장애 시 복구 및 상태 확인 가능

따라서 기존 수동 실행 방법을 개발·진단 용도로 남기고, 실제 기본 운영 방식은 자동 실행으로 변경한다.

## 4. 비밀 키 보관

Pairper 프로젝트별 `.env` 파일을 사용한다.

기본 위치:

`D:\project\18_pairper\.env`

사용자가 이미 작성한 `.env` 파일이 있다면 **내용을 덮어쓰거나 재생성하지 않는다.**

필요한 설정 값은 다음과 같다.

- `CONTROL_PLANE_API_KEY` — 터널 인증용 `sk-proj-...` 비밀 키
- `CONTROL_PLANE_TUNNEL_ID` — `tunnel_...` 형식의 터널 식별자
- `PAIRPER_DATA_DIR` — 선택적인 Pairper 데이터 저장 경로

`key_...` 형식의 Tracking ID를 인증 키로 사용하지 않는다.

비밀값을 코드·문서·로그·커밋 메시지에 포함하지 않는다.

### .gitignore 수정

최소한 다음 파일과 경로를 Git 추적에서 제외한다.

- `.env`
- `.env.*` — 단, `.env.example`은 예외
- `.pairper/`의 런타임 데이터
- 터널 실행 로그와 임시 파일
- 인증 정보 및 런타임 자격 파일

`.env.example`에는 변수 이름과 설명만 넣는다.

실제 API 키는 넣지 않는다.

이미 `.env`가 Git에 추적되고 있다면 추적 상태를 검사하고, 실제 비밀값을 출력하지 않은 상태에서 안전하게 추적을 해제한다.

키가 이미 Git 이력에 포함된 것이 확인되면 해당 사실과 키 교체 필요성을 보고한다.

Windows에서는 `.env`의 파일 접근 권한을 현재 사용자 중심으로 제한한다.

### 환경변수 정책

`.env`의 값을 Windows 사용자 또는 시스템의 영구 환경변수에 저장하지 않는다.

실행 스크립트가 `.env`를 읽어 **자신과 자식 프로세스의 실행 환경에만** 필요한 값을 전달한다.

`tunnel-client`는 `.env`를 자동으로 읽지 않으므로 별도의 로딩 과정이 필요하다.

`.env`를 읽는 과정에서 PowerShell `Invoke-Expression` 또는 임의 코드 실행 방식은 사용하지 않는다.

지원할 `.env` 문법을 명확하게 정의하고, 빈 값·중복 키·잘못된 형식은 진단 가능한 오류로 처리한다.

## 5. 터널 클라이언트 연결 프로필

사용 중인 터널 클라이언트는 다음 버전이다.

`tunnel-client v0.0.16`

로컬 실행 파일의 현재 위치:

`D:\tools\tunnel-client-v0.0.16-windows-amd64\tunnel-client.exe`

다만 설치 경로는 사용자가 변경할 수 있으므로 하드코딩만으로 처리하지 않는다.

프로젝트 설정 또는 런처의 명시적인 경로 설정을 통해 관리한다.

### 연결 방식

공식 `sample_mcp_stdio_local` 구성에 맞춘다.

MCP의 `main` 채널에 기존 Pairper 서버를 연결한다.

실행 대상:

`D:\project\18_pairper\.venv\Scripts\python.exe -m pairper.mcp.server`

기존 서버의 `stdio` 인터페이스는 유지한다.

HTTP MCP 서버로 전환하거나 별도의 Railway 서버를 만들지 않는다.

### 프로필 저장

터널 프로필은 프로젝트별로 관리한다.

예:

`.pairper/tunnel-client.yaml`

설정은 다음 내용을 포함한다.

- `config_version: 1`
- `control_plane.tunnel_id`
- `control_plane.api_key`
- `mcp.commands`의 `main` 채널
- 로컬 MCP 실행 명령
- 로컬 health endpoint
- 로그 수준과 로컬 관리 UI 설정

인증 키는 YAML 안에 직접 기록하지 않는다.

`tunnel-client`가 지원하는 `env:CONTROL_PLANE_API_KEY` 참조를 사용한다.

필요하면 `file:` 비밀 참조 방식도 검토할 수 있다. 단, 사용자가 이미 정한 `.env` 중심의 키 관리 원칙을 우선한다.

프로필 생성은 반복 실행해도 기존 정상 설정과 사용자 키를 불필요하게 변경하지 않도록 구현한다.

## 6. 실행 스크립트 구현

다음과 같이 역할을 분리한다.

**`start-pairper-tunnel.ps1`**

- 프로젝트의 `.env` 로딩
- 필수 설정 검증
- 터널 클라이언트 실행 파일 존재 여부 확인
- Pairper Python MCP 실행 경로 확인
- 터널 프로필 준비
- `tunnel-client run` 실행
- 로그 기록 및 종료 상태 보고

**`test-pairper-tunnel.ps1`**

- 설정 파일 검사
- 실행 경로 확인
- `tunnel-client doctor --explain` 실행
- 오류 발생 단계 보고
- 민감 정보 마스킹

**`install-pairper-autostart.ps1`**

- Windows 작업 스케줄러에 자동 시작 등록
- 기존 동일 작업이 있다면 중복 등록 방지
- 등록 결과 및 실행 설정 확인

**`uninstall-pairper-autostart.ps1`**

- Pairper용 자동 실행 등록 해제
- 다른 프로그램의 시작 작업에는 영향 없음

기존 `start-pairper.ps1`는 GUI 실행을 계속 담당한다.

GUI 시작과 MCP 터널 시작을 반드시 묶지 않는다.

### 보안 규칙

- 비밀 키를 PowerShell 명령줄 인수로 직접 전달하지 않는다.
- 로그에 `.env` 전체 내용을 출력하지 않는다.
- 환경변수 값을 진단 목적으로 출력하지 않는다.
- 예외 메시지에도 API 키가 포함되지 않도록 한다.
- 외부에서 전달받은 임의 명령을 실행하지 않는다.
- 터널 클라이언트가 사용할 MCP 명령은 지정된 Pairper 실행 경로로 제한한다.

## 7. Windows 로그인 시 자동 시작

Windows 작업 스케줄러를 사용한다.

작업 이름은 다음과 같이 지정한다.

`Pairper MCP Tunnel`

### 트리거

**현재 Windows 사용자 로그인 시 실행**

로그인 전에 실행되는 Windows 서비스는 만들지 않는다.

### 실행

`start-pairper-tunnel.ps1`을 실행한다.

스크립트의 절대 경로와 작업 디렉터리를 정확하게 지정한다.

필요하면 로그인 직후 약간의 지연을 두어 네트워크 초기화 시간을 확보한다.

관리자 권한이 필요하지 않다면 일반 사용자 권한으로 실행한다.

### 중복 실행 방지

같은 사용자가 로그인을 반복하거나 자동 시작 작업이 중복 호출되어도 동일한 터널 클라이언트가 여러 개 실행되지 않도록 한다.

기존 프로세스의 실제 상태를 검사한 후 필요한 경우에만 실행한다.

### 장애 복구

- 일시적인 네트워크 오류에서는 터널 클라이언트의 재연결 동작을 활용한다.
- 프로세스가 비정상 종료되면 작업 스케줄러의 재시작 정책으로 복구한다.
- 재시작 간격과 횟수에 상한을 둔다.
- 영구적인 인증 실패가 발생하면 무한 반복 대신 오류를 기록한다.
- Windows 작업 스케줄러의 기본 실행 시간 제한이 장기 실행 터널을 자동 종료하지 않도록 설정한다.

### 종료 조건

Windows 사용자가 로그아웃하거나 PC를 종료하면 연결이 종료되어도 된다.

로그인 전에 별도의 시스템 서비스로 실행할 필요는 없다.

작업 등록은 사용자가 설치 스크립트를 실행했을 때 수행한다. 프로그램을 단순히 실행하거나 테스트했다고 시스템 시작 설정을 몰래 변경하지 않는다.

## 8. 연결 상태 확인

터널이 실행 중이라는 사실과 ChatGPT가 실제 MCP 도구를 호출할 수 있다는 사실은 구분해야 한다.

다음 상태를 확인할 수 있어야 한다.

- 설정 누락
- 실행 파일 없음
- 인증 실패
- 터널 연결 시도 중
- 로컬 터널 런타임 준비 완료
- ChatGPT 도구 호출 확인
- 연결 끊김

로컬 health endpoint는 외부 네트워크가 아닌 `127.0.0.1`에만 바인딩한다.

기본 포트 충돌을 피할 수 있도록 사용 가능한 포트 또는 동적 포트 방식을 검토하고, 실제 관리 UI 주소를 확인할 수 있도록 한다.

`/healthz`와 `/readyz`는 구분하여 검사한다.

특히 stdio MCP에서는 런타임이 준비되었다는 사실만으로 실제 도구 호출이 성공했다고 판단하지 않는다.

### 사용자 안내

프로그램에서 MCP 연결 상태를 간단하게 확인할 수 있도록 한다.

최소한 다음 정보를 제공한다.

- 연결 상태
- 마지막 정상 통신 또는 진단 시각
- 연결 문제 발생 시 간단한 오류 메시지
- 자세한 연결 진단을 여는 기능

실제 터널 준비 확인 전에는 '연결 완료'라고 표시하지 않는다.

## 9. 첫 연결 검증

자동 시작 등록 전에 수동 실행으로 다음 과정을 검증한다.

1. `.env`에 필요한 항목이 존재하는지 확인
2. `tunnel-client doctor --explain` 통과
3. `tunnel-client run` 실행
4. 로컬 관리 UI와 readiness 확인
5. ChatGPT에서 Pairper 커스텀 MCP 등록
6. `list_papers` 호출
7. 실제 로컬 SQLite의 논문 목록과 응답 비교
8. `get_page_image`를 통한 PDF 페이지 이미지 전달 확인
9. 테스트 논문을 이용한 MCP 쓰기 도구 호출 및 로컬 저장 확인

ChatGPT에서 커스텀 MCP를 등록하는 작업은 사용자 설정 화면에서 진행한다.

로컬 검사 성공만으로 ChatGPT 연동 완료라고 보고하지 않는다.

연결이 검증된 뒤 자동 시작을 등록하고 다음을 다시 확인한다.

- Windows 로그아웃 후 재로그인
- 사용자 조작 없이 터널 실행
- ChatGPT에서 Pairper 도구 호출
- 기존 데이터 유지
- 중복 터널 프로세스 없음

# Part B. TypeScript 프론트엔드 전환

## 10. 기술 변경의 배경

기존 Pairper의 UI는 PySide6 Qt 위젯으로 작성되어 있으며, 논문은 Python이 생성한 HTML을 QtWebEngine에서 표시한다.

초기 기능 검증을 위해서는 적절하지만, 향후 논문 블록별 UI, 상호작용, 디자인 개선, 번역 표시, 설명 기능 등을 추가하기에는 TypeScript 기반 컴포넌트 구조가 더 적합하다고 판단했다.

사용자는 다음 기술 방향을 결정했다.

- **프론트엔드: TypeScript**
- **백엔드: Python 또는 TypeScript**

현재 구현된 Python의 PDF 처리와 MCP 서버는 재사용할 가치가 크므로, 이번 작업에서는 Python 백엔드를 유지하고 프론트엔드를 React + TypeScript로 전환하는 방식을 우선 사용한다.

백엔드를 TypeScript로 전부 재작성하지 않는다.

---

## 11. 권장 구성

- 데스크톱 셸: 기존 PySide6 유지
- 프론트엔드: React + TypeScript
- 빌드 도구: Vite
- 논문 수식: KaTeX
- PDF 분석: 기존 PyMuPDF
- 로컬 데이터베이스: 기존 SQLite
- MCP: 기존 Python MCP SDK
- 프론트엔드·백엔드 통신: 제한된 Qt WebChannel 브리지

이는 기존 코드를 최소한으로 변경하면서 TypeScript UI의 장점을 활용하기 위한 선택이다.

기존 QtWebEngine을 즉시 제거하거나 Electron·Tauri로 전면 전환하지 않는다.

React + TypeScript 빌드 결과물을 로컬 애플리케이션에 포함하여 오프라인 실행을 지원한다.

개발용 Vite 서버가 실행되지 않아도 배포된 프로그램은 정상 작동해야 한다.

## 13. 기본 UI 구성

아직 최종 시각 디자인이 확정되지 않았으므로 기존 기능을 보존하는 읽기 중심 레이아웃을 먼저 구현한다.

### 상단 영역

- Pairper 로고 또는 텍스트
- PDF 추가 버튼
- MCP 연결 상태
- 연결 설정 또는 진단 접근

### 왼쪽 영역

논문 목록을 표시한다.

논문을 선택하면 해당 문서를 오른쪽에서 연다.

### 오른쪽 영역

논문 본문이 표시되는 주요 읽기 공간이다.

본문은 가독성 있는 최대 너비를 유지하고 가운데 정렬한다.

2단 PDF도 하나의 열로 표시한다.

수식과 표가 너비를 초과하면 해당 블록만 가로 스크롤을 허용한다.

### 기본 원칙

- 원문 텍스트는 임의로 수정하지 않는다.
- PDF의 페이지 구분을 강제로 표시하지 않는다.
- 제목·본문·표·수식·그림의 구분이 명확해야 한다.
- 원본 영역 대조 기능을 유지한다.
- 미처리 논문을 선택하면 처리 대기 상태를 보여준다.
- 오류 및 검토 필요 상태를 표시한다.

디자인의 세부 색상과 브랜드 스타일은 추후 별도로 결정할 수 있도록 CSS를 컴포넌트 구조와 분리한다.

## 14. Python과 TypeScript 연결

Python은 데이터 처리와 보존을 담당한다.

TypeScript는 이미 구성된 문서 데이터의 표시와 사용자 상호작용을 담당한다.

기존 Python 코드를 TypeScript가 직접 복제하지 않는다.

### 데이터 흐름

1. Python이 등록된 논문 목록을 조회한다.
2. TypeScript UI가 목록을 표시한다.
3. 사용자가 논문을 선택한다.
4. TypeScript가 논문 ID를 Python에 전달한다.
5. Python이 유효한 문서 뷰와 원본 참조 정보를 읽는다.
6. 프론트엔드 렌더링에 필요한 안전한 데이터 모델을 반환한다.
7. React가 문서 블록을 표시한다.

Qt WebChannel 등의 브리지에는 명확하게 제한된 기능만 노출한다.

임의 로컬 파일 읽기, 셸 명령 실행, 전체 디렉터리 접근 기능을 프론트엔드에 제공하지 않는다.

브리지 입력은 논문 ID 등의 검증된 값으로 제한한다.

React에서 표시하는 문서는 기존 Pydantic 문서 스키마와 일관되어야 한다.

Python에서 원본 span ID를 안전하게 해석하고, 프론트엔드는 검증된 표시용 데이터만 받도록 한다.

스키마가 달라질 경우 버전 관리와 호환성 검사를 제공한다.

API 키와 터널 인증 정보는 프론트엔드에 절대로 전달하지 않는다.

## 15. 기존 논문 렌더러 보존 및 교체

현재 Python HTML 렌더러의 다음 기능을 유지한다.

- 원문 span ID 참조
- 줄 결합 및 하이픈 결합 이력
- 인라인 수식
- 블록 수식
- 병합 셀 표
- 원본 그림 영역 렌더링
- 수식 및 표의 원본 fallback
- 원문 대조 기능
- HTML 인젝션 및 외부 파일 접근 방지

React 렌더러가 이 기능을 모두 재현하기 전에는 Python 렌더러를 제거하지 않는다.

가능하면 같은 문서 데이터로 Python 렌더러와 TypeScript 렌더러의 출력 내용을 비교한다.

특히 기존 코드에서 확인된 서로 다른 TextRun 사이의 공백 연결 문제를 점검한다.

단어, 공백, 하이픈, 인라인 수식 경계에서 원문 내용이 변경되지 않도록 한다.

수식과 표가 검증되지 않았다면 원본 영역 이미지 fallback을 유지한다.

기존 12개 문서 블록 지원 범위가 줄어들어서는 안 된다.
